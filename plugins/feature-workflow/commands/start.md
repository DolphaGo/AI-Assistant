# /feature-workflow:start

새 워크플로우의 1~2단계를 자동 진행한다.

## 사용법

```
/feature-workflow:start <작업 이름 | 이슈/티켓 URL·ID>
/fw-start order-data-migration
/fw-start https://jira.example.com/browse/PROJ-123
```

`<작업 이름>` 은 `docs/<이름>/` 디렉토리와 STATE.json 의 `workflow` 에 그대로 사용된다.
이슈/티켓이 주어지면 티켓 ID 를 작업 이름으로 쓰되 **항상 대문자로 정규화한다**
(예: `proj-123` 으로 입력받아도 `docs/PROJ-123/`) — 그 외 가공은 하지 않는다.
**작업 이름 = docs 디렉토리명 = 브랜치의 `feature/` 뒤 이름은 항상 같은 문자열이어야 한다**
(아래 3번 참조 — 사용자가 신경 쓸 일이 아니라 이 스킬이 지키는 규칙이다).

## 동작

1. **먼저 기존 문서에 앵커링** — 리포의 CLAUDE.md 와 기존 `docs/*/PLAN.md` 의 §핵심 결정·
   §용어를 훑어 이미 정해진 관례를 파악한다. **문서를 읽으면 답이 나오는 것은 묻지 않는다.**

2. **이슈/티켓 컨텍스트 (해당 시)** — 인자(또는 사용자 요청)에 이슈 트래커 URL·티켓 ID 패턴
   (예: `PROJ-123`, `https://…/browse/PROJ-123`, GitHub issue URL)이 있으면:
   - 현재 세션에 그걸 읽을 수 있는 도구가 있으면(이슈 트래커 MCP, 웹/이슈 읽기 도구 등) 제목·설명·
     코멘트를 가져와 아래 인터뷰(목표 한 문장·모호점)의 **추천 답안** 재료로 쓴다.
     **특정 벤더에 종속되지 않는다** — 읽을 도구가 없으면 내용을 붙여넣어 달라고 요청하고
     진행한다(막지 않는다).
   - 티켓 ID 는 브랜치 이름 추천과 `docs/<이름>/` 디렉토리명에 반영하고, PLAN.md 에
     티켓 링크를 남긴다.

3. **작업 위치(브랜치) 합의** — 어디서 작업할지 `현재 환경의 사용자 질문 수단`/`request_user_input`/직접 질문 등 현재 환경의 사용자 질문 수단 으로 먼저 정한다.
   prefix·base 브랜치는 **강제하지 않고 리포 관례를 감지해 추천만 한다** (브랜치 전략은
   사용자에게 위임 — PLAN D1 계열 원칙):
   - **새 브랜치 분기 (대개 추천)** — `<prefix>/<이름>` 을 base 브랜치에서 분기해 체크아웃.
     리포에 `develop` 브랜치가 있으면 git flow 로 보고 base 로 develop 을 추천하며, 그때는
     "git flow 관례에 따라 develop 기준으로 분기합니다" 라고 사용자에게 명시한다. 없으면
     기본 브랜치를 추천. 기존 브랜치 목록에 `feature/*` 같은 prefix 관례가 보이면 그 prefix,
     티켓 기반이면 `feature/<티켓ID>` 를 추천한다 — 티켓 ID 는 **항상 대문자**
     (예: `feature/PROJ-123`, 절대 `feature/proj-123` 아님).

     **브랜치 이름은 `feature/<작업 이름>` — 작업 이름(=docs 디렉토리명=STATE `workflow`)과
     정확히 같은 문자열로 만든다(대소문자 포함).** 이유: 하네스는 PR 머지 후 작업 브랜치를
     `origin/<base>` 최신 위로 재생성(§26 M5)하는데, 그 대상 판정이 "브랜치명 ==
     `feature/<workflow>` 정확 일치"다. 이름이 어긋나면 하네스가 사용자 소유 브랜치로 보고
     건너뛰어, squash 머지 환경에서 다음 phase PR 에 이전 phase diff 가 중복해 담긴다.
     이 일치는 사용자에게 요구하는 규칙이 아니라 **이 스킬이 브랜치·디렉토리를 만들 때
     스스로 지키는 규칙**이다 — 사용자가 다른 브랜치 이름을 원하면 그 이름에 맞춰 작업
     이름(docs 디렉토리)을 정하면 된다.

     **분기 절차 — 원격과 로컬 일치가 선행 조건이다** (로컬 base 가 뒤처진 채 분기하면
     시작부터 stale 브랜치가 된다):
     1. 워킹트리가 깨끗한지 확인 — 더러우면 커밋/stash 를 사용자에게 묻는다
     2. `git fetch origin <base>` 로 원격 최신을 먼저 받는다 — **항상 분기 전에 수행**
     3. `git checkout -b <prefix>/<이름> --no-track origin/<base>` — 로컬 base 브랜치를
        거치지 않고 원격 최신 기준으로 직접 분기한다(로컬 base 를 pull 로 갱신할 필요도,
        로컬 base 가 뒤처져 있어도 문제가 없다). `--no-track` 필수 — 생략하면 git 이
        upstream 을 origin/<base> 로 자동 설정해, `push.default=upstream` 환경에서
        `git push` 가 base 브랜치로 나가는 사고가 난다(하네스 §41 에서 실측된 결함과
        동일한 축)
     4. 원격이 없거나(로컬 전용 리포) fetch 가 실패하면: 막지 않되 사용자에게 알리고
        로컬 `<base>` 기준으로 분기할지 확인받는다

     생성 후 STATE.json 의 `base_branch` 를 분기 기준 브랜치로 적는다 — 하네스의 `isolate`
     전략은 이미 base 가 아닌 브랜치에 있으면 **그 브랜치를 그대로 작업 브랜치로 삼아
     감시**하므로 추가 설정이 필요 없다.
   - **현재 브랜치에서 진행** — 브랜치를 만들지 않고 STATE.json `branch_strategy` 를
     `"current"` 로 적는다 (하네스 이탈 감시 제외 — 사용자 위임).
   - **하네스 자동 격리** — 지금은 아무것도 하지 않는다. 기본값(`isolate`)대로 `fw run`
     시점에 base 위에 있으면 `feature/<workflow>` 브랜치가 자동 생성된다.

4. 사용자에게 다음을 물음 (모든 질문에 **추천 답안 동봉** — 백지에서 시작하지 않게):
   - 작업의 명확한 목표 (한 문장으로)
   - 모호하다고 판단되는 부분 1~3개 (`현재 환경의 사용자 질문 수단`/`request_user_input`/직접 질문 등 현재 환경의 사용자 질문 수단)
   - **기존 관례와 충돌하는 지점이 있으면 그것부터** ("리포는 X 관례인데 이번 요청은 Y 를
     함의합니다 — 어느 쪽입니까?")
   - 참조할 프로젝트/예시가 있는지
   - 커밋 author/검증 명령 등 메타 정보 (브랜치는 3번에서 이미 합의됨)

5. **PR 을 잘게 나눌지 합의** — `현재 환경의 사용자 질문 수단`/`request_user_input`/직접 질문 등 현재 환경의 사용자 질문 수단 으로 묻는다. **이 질문을 건너뛰지 마라.**
   이 설정은 STATE.json 을 직접 열어 고치는 것 말고는 켜는 길이 없고, 정작 가장 필요한
   때(작업이 큰 때)가 사용자가 설정을 떠올릴 여유가 가장 없는 때다.

   질문은 **"PR 을 잘게 나눌까요?"** 로 묻는다 — "조각 PR을 켤까요", "review_split 을
   활성화할까요" 처럼 내부 용어로 묻지 않는다. 사용자는 설정 이름이 아니라 리뷰가 어떻게
   달라지는지를 결정하는 것이다.

   **묻기 전에 그림을 먼저 보여준다.** 브랜치가 어떻게 되는지는 말로 설명하면 잘 전달되지
   않는다. 3번에서 합의한 실제 브랜치 이름과 base 를 넣어 그린다(아래는 base 가 `develop`,
   작업 이름이 `PROJ-123` 인 예):

   ```
   feature/PROJ-123-1 ──PR──▶ ┐
   feature/PROJ-123-2 ──PR──▶ ├─ feature/PROJ-123 ──PR──▶ develop
   feature/PROJ-123-3 ──PR──▶ ┘

     조각 PR — 작게, 하나씩 리뷰          통합 PR — 승인만
   ```

   그리고 이 두 가지를 함께 말한다:
   - 조각 PR 은 **base 로 바로 가지 않고 통합 브랜치에 모입니다.** 그래서 조각이 그 자체로
     완결일 필요가 없고, "인터페이스만 추가 → 구현 → 호출부 교체" 처럼 나눌 수 있습니다.
   - 마지막 통합 PR 은 diff 가 전체지만 **조각별로 이미 리뷰가 끝났으므로** 승인만 받으면
     됩니다.

   **추천 기준** (추천 답안을 반드시 동봉한다):
   - phase 가 여러 개거나, 한 phase 가 여러 파일·여러 관심사를 건드릴 것으로 보이면 **켜기를
     추천**한다. 근거를 한 줄로 말한다("Phase 2 가 스키마와 API 를 함께 건드려 보입니다").
   - 한 phase 로 끝나는 작은 작업이면 **끄기를 추천**한다 — 머지 횟수만 늘어난다.

   **켤 수 없는 경우를 먼저 확인한다** (묻고 나서 안 된다고 하면 안 된다):
   - 3번에서 **"현재 브랜치에서 진행"**(`branch_strategy: "current"`)을 골랐으면 이 조합은
     하네스가 시작 시점에 거부한다 — 조각 브랜치를 하네스가 만들어야 하는데 `current` 는
     브랜치를 사용자에게 위임하는 전략이다. 이때는 묻지 말고, "지금 전략에서는 쓸 수
     없습니다" 를 한 줄로 알리고 넘어간다.
   - 조각은 통합 브랜치로 **머지되어야** 다음 조각이 그 위에서 시작하므로 `pr_mode: true` 가
     필요하다. 켜기로 했으면 `pr_mode` 도 함께 켜고, PR 머지가 사람 손을 필요로 한다는 것을
     명시한다(하네스는 PR 을 만들고 기다린다 — 머지는 사람만 한다).

   켜기로 했으면 STATE.json 에 다음을 적는다:

   ```json
   "pr_mode": true,
   "review_split": { "enabled": true, "budget_lines": 400 }
   ```

   `budget_lines` 는 조각 하나의 **목표** 라인 수다(상한이 아니다 — 넘어도 진행을 막지 않고
   실행 로그에 남는다). 코드+테스트만 세고 워크플로우 문서(`docs/<이름>/`)는 제외한다.
   특별한 근거가 없으면 400 을 쓴다.

6. 답변을 종합해 `docs/<작업 이름>/` 아래에 다음 3개 파일 생성:
   - `PLAN.md` — 변하지 않는 마스터 플랜. **§핵심 결정은 표(ID·근거·상태·날짜)로, §용어도
     표로 채운다** — 하네스가 이 절을 파싱해 무인 세션에 주입하므로 산문이면 안 된다.
     해소된 결정은 여기에 **즉시** 적는다(인터뷰 끝나고 몰아서 X).
   - `NOTES.md` — 사람용 진행 메모 (이관 맵/리스크/결정 배경 — phase 상태 표는 STATE.json 소관)
   - `STATE.json` — 하네스(fw)용 기계 상태. `templates/STATE.json` 기반으로
     PLAN 의 phase 표와 동일한 phases 배열을 채운다 (id/title/depends_on/verify).
     **phase 별 `next_steps` 에 Phase 1(과 알고 있다면 이후 phase)의 상세 작업 단계를
     채운다** — 다음 세션이 이어받을 때 참고하는 유일한 자리이므로 비워두지 않는다.
     verify 명령은 반드시 실패 시 non-zero exit 하는 것으로 — `true`/`echo`/`|| true`/
     `| tee` 처럼 항상 성공하거나 실패를 삼키는 명령은 하네스 검증 게이트를 무력화하며,
     `fw run` 이 시작 시점에 이를 감지해 실행 자체를 거부한다(§26 I5 잔여 승격 — 세션은
     한 번도 spawn 되지 않는다). `fw doctor <dir>` 로 미리 점검할 수 있다.

7. 사용자에게 첫 phase 시작 의사를 물음.

## 산출물 템플릿

`templates/PLAN.md`, `templates/NOTES.md`, `templates/STATE.json` 파일을 베이스로 하되, 사용자 답변으로 채운다.

## 안티 패턴

- 사용자 답변 없이 임의로 채우기
- 한 번에 너무 많이 묻기 (4개 이하 유지)
- 첫 phase 까지 한 번에 진행하기 — 문서 검토 단계를 건너뛰지 말 것
- **PR 분할 질문(5번)을 조용히 건너뛰기** — 묻지 않으면 사실상 영원히 꺼진 상태로 남는다
- 내부 설정 이름으로 묻기 (`review_split`, `budget_lines`) — 사용자가 결정하는 것은 설정이
  아니라 "리뷰를 어떻게 받을지" 다
- 브랜치 관계를 그림 없이 말로만 설명하기
