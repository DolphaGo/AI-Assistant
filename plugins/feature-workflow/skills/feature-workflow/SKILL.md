# Feature Workflow — 근거 기반 기본 작업 방식

매 대화에서 이 스킬을 기본 진입점으로 사용한다. 근거 법칙은 사실 주장에 적용하고,
기록의 양은 작업에 맞춘다. 대화마다 형식적인 시작 선언이나 검증 보고를 반복하지 않는다.

## 1. 답변과 판단의 근거

- 확정 문장은 이번 작업에서 직접 읽은 원천(소스·설정·로그·실행 결과·사용자 자료)으로만 쓴다.
  기억·관례·이전 AI 문서·PLAN/NOTES/STATE는 탐색과 재개의 단서이며 현재 동작의 증거를 대체하지 않는다.
- 사실마다 다시 확인 가능한 출처를 붙인다: `file:line`, 커맨드와 실제 출력, URL과 확인 시각,
  특정 커밋, 사용자 제공 자료. 같은 근거를 공유하는 문장은 묶어서 출처를 붙일 수 있다.
- 조회·실행으로 확인 가능한 것은 확인한다. 확인 수단이 없을 때만
  `미확정: <내용> — <확정에 필요한 원천>`으로 남긴다.
- 식별자·타입·경로·에러 메시지·수치는 원문대로 유지한다. 목록을 “등”으로 축약하거나
  토큰의 의미를 이름만 보고 풀지 않는다.
- 조건부 동작은 대상·분기·guard·결과를 함께 적는다. 확인 범위를 넘는 포괄 문장을 쓰지 않는다.
- 관측 사실, 해석·판정, 설계 제안, 사용자 결정을 구분한다. 창작·제안은 확정 사실로 포장하지 않는다.
- 충돌은 양쪽 출처를 남긴다. 실제 실행을 결정하는 코드·설정을 주석·문서보다 우선한다.
- 로컬 검사, 실제 계정 접근, 실환경 실행, 외부 전달, 배포를 각각 구분한다.
  설정 저장이나 빌드 성공으로 실행·전달·배포 성공을 주장하지 않는다.
- 2차 기록밖에 없으면 `2차 기록 — 1차 원천(<무엇>) 미확보`를 표시한다.

## 2. 작업 크기에 따라 기록

| 대상 | 진행 방식 |
|---|---|
| 짧은 질문·단순 조회·가벼운 대화 | 파일 없이 답변. 사실은 출처와 불확실성을 점검한다. 별도 원장·서브에이전트·보고서 없음 |
| 작은 수정·조사·리뷰·문서 작성 | 바로 수행하되 남겨야 할 결정·근거·검증이 있으면 기존 워크플로우에 기록하거나 1개 phase의 간단한 세 파일 생성 |
| 여러 단계·긴 작업·세션 간 재개 | 요구 파악 → PLAN → phase 실행 → 검증 → 기록 갱신 → 재개/마무리 |

사용자가 기록을 원치 않거나 별도 위치·형식을 지정하면 그 지시를 우선한다.
순수 아이디어·창작에는 사실 검수 전체를 적용하지 않는다. 그 안의 사실 주장에는 §1을 적용한다.
파일을 고쳤다는 이유만으로 큰 프로젝트 절차를 만들지 않는다.

## 3. 기록은 세 파일로 통일

기본 위치는 작업 저장소의 `docs/<workflow>/`. 저장소가 없으면 허용된 작업 공간의
`docs/<workflow>/`를 사용한다. 다른 위치를 지정받았으면 그 위치를 쓴다.
기존 파일이 있으면 내용을 보존하고 필요한 절만 보강한다.

| 파일 | 역할 |
|---|---|
| `PLAN.md` | 목표·범위·접근·phase 목록·검증 기준·핵심 결정 표(ID·결정·근거·상태·날짜)·용어 |
| `NOTES.md` | 확인한 사실과 출처(F ID)·검증 명령과 실제 결과(V ID)·미확정·원천 충돌·트러블슈팅·결정 배경·검수 결과 |
| `STATE.json` | phase 목록·상태·시도·PR·`next_steps` 등 기계가 읽는 작업 상태 |

- `NOTES.md`의 **확인한 사실**이 근거 원장 역할을 한다. 별도 `ledger.md`, `output.md`,
  `review-*.md`, `DECISIONS.md`를 중복 관리하지 않는다. 산출물은 실제 코드·문서·PR 본문 위치에서 검수한다.
- 위 세 파일은 **워크플로우 관리 기록**이다. 사용자가 요청한 코드·보고서·스펙 산출물까지 세 파일로 제한하지 않는다.
- PLAN 초안의 결정은 PLAN에 기록한다. 확정 후 구현·verify 중 새 결정·제안·충돌은 즉시 NOTES에 기록하고,
  PLAN 반영은 아래 §3.1의 개정 절차에서만 한다. 뒤집힌 결정은 삭제하지 않고 `superseded by D<n>`으로 남긴다.
  제안은 `proposed`, 사용자 승인 또는 위임 범위에서 확정한 결정은 `accepted`로 구분한다.
- PLAN의 phase 제목·개수·순서는 STATE와 일치시킨다. 현황 표는 NOTES에 복제하지 않는다.
- STATE는 **기록된 상태**의 관리 기준이다. 현재 소스·Git·실행 결과와 다르면 그 차이를 확인하고 수정한다.
- 스키마가 strict인 하네스와 호환되도록 근거·검수용 JSON 키를 임의로 추가하지 않는다.
- 토큰·비밀번호·민감한 원문 로그를 기록하거나 커밋하지 않는다. 필요한 결과만 마스킹해 인용한다.

템플릿: [PLAN](../../templates/PLAN.md), [NOTES](../../templates/NOTES.md), [STATE](../../templates/STATE.json).
템플릿의 설명·예시·빈칸은 실제 근거가 아니다. 사용 시 작업에 맞게 채운다.

### 3.1 확정 PLAN 고정과 개정

**초안 → 확정·고정 → 구현 → verify → 결과·피드백 기록 → 필요한 PLAN 개정 → 재확정·고정** 순서를 따른다.

- 구현 전에 PLAN에 확정 여부·시점·승인 또는 위임 근거를 적고, NOTES에 확정본의 Git 커밋 또는 파일 해시를 기록한다.
  이미 승인된 계획을 다시 승인받을 필요는 없다. 기존 계획으로 구현이 시작됐다면 확정본으로 취급한다.
- 확정된 `PLAN.md`는 구현과 verify 동안 파일 전체를 수정하지 않는다. 목표·범위·접근·phase 목록·검증 기준·
  결정·용어뿐 아니라 진행률·완료 표시·오탈자도 이 기간에는 바꾸지 않는다. 진행과 발견 사항은 NOTES·STATE에만 기록한다.
- 구현 결과나 실패에 맞춰 목표·검증 기준을 낮추거나 phase를 사후 변경하지 않는다. STATE의 `next_steps`로
  계획 변경을 우회하지 않는다. phase 종료나 테스트 한 번의 통과만으로 PLAN 고정이 해제되지 않는다.
- verify는 해당 구현의 기준이 된 확정 PLAN으로 수행하고, PLAN 대비 충족·미충족·실패·미검증과 실제 근거를 NOTES에 남긴다.
  이어 NOTES에 피드백의 작성 주체(사용자·검수자·자체 검토), 지적·변경 제안·수용/보류 판단·이유를 기록한다.
  사용자 피드백을 받지 않았다면 받았다고 쓰지 않는다. verify 결과와 피드백 기록이 모두 있어야 PLAN을 개정할 수 있다.
- 구현 중 새 요구·충돌·실행 불가로 계획 변경이 필요하면 그 변경에 의존하는 작업을 멈추고 NOTES에 기록한다.
  전체 완료를 기다리는 대신 기존 PLAN 기준으로 가능한 범위를 verify하고, 미완료·미검증 항목과 사유를 남긴 뒤
  피드백·개정 단계로 전환한다. 실패 또는 미검증이 남아 있어도 개정은 가능하지만 완료·통과로 표시하지 않는다.
- 개정할 때는 NOTES에 이전 확정본, 대응 verify·피드백, 변경 전후·이유·권한 근거를 연결한다.
  기존 결정은 이력을 보존하고, phase를 바꾸면 PLAN과 STATE 목록을 함께 맞춘다. 무인 실행의 STATE는 하네스가 갱신한다.
  기존 위임 범위를 벗어나거나 사용자 결정과 충돌하는 선택만 확인한다. 개정본을 재확정·고정한 뒤 구현과 verify를 다시 수행한다.
- 변경이 필요 없으면 PLAN을 그대로 두고 NOTES·STATE만 마무리한다. 하네스의 파일 쓰기 권한은 이 개정 순서를 생략할 근거가 아니다.

## 4. 실행과 재개

1. 사용자 목표와 기존 결정을 확인한다. 원천으로 답이 나오는 것은 직접 확인한다.
   결과를 바꾸는 미결 선택·권한·사용자 결정 충돌만 묻고, 독립적인 작업은 계속한다.
2. 기존 PLAN·NOTES·STATE를 읽고 **관련 원천과 현재 상태를 대조**한다.
   Git 작업이면 저장소·브랜치·`git status`·현재 커밋을 확인한다.
   과거 검증 결과를 현재 결과로 재사용하지 않는다. 의미 있는 차이가 있으면 NOTES에 근거와 함께 기록한다.
3. 새 작업이면 목표·범위·검증 기준·의존 순서를 PLAN에 적는다.
   작은 작업은 한 phase로 충분하다. §3.1에 따라 구현 전에 PLAN을 확정·고정한다. 이미 받은 승인·결정·작업 권한을 다시 묻지 않는다.
4. STATE의 현재 phase `next_steps`를 참고해 확정 PLAN 안에서 작업한다. 현재 원천과 충돌하는 낡은 지시는 그대로 실행하지 않는다.
   계획 변경이 필요하면 PLAN을 즉시 고치지 말고 §3.1의 중단·verify·피드백·개정 순서를 따른다.
5. 사실을 쓰기 전에 NOTES의 사실 행에 원천과 조건을 기록한다. 원장에 없는 사실이 필요하면
   먼저 원천을 확인하고 행을 추가한다. 판정·추론은 사실 표 밖에서 대응 F ID와 함께 쓴다.
6. 변경에 맞는 검증을 실행하고 실제 명령·출력 요지·종료 코드·대상 범위를 NOTES에 기록한다.
   실패를 성공으로 바꾸는 `|| true` 같은 명령을 완료 근거로 쓰지 않는다.
7. §5의 대조와 필요한 구현 교정을 끝낸 뒤 완료 상태와 다음 phase의 구체적인 `next_steps`를 갱신한다.
   기준·범위 자체를 바꾸는 교정은 §3.1을 따른다. 완료를 위해 PLAN을 결과에 맞춰 수정하지 않는다.
   실패·미검증·상한 도달이면 완료로 위장하지 않고 필요한 후속 작업을 남긴다.
8. 승인된 범위 안에서는 다음 단계까지 진행한다. phase마다 기계적으로 재승인을 요구하지 않는다.
   커밋·push·PR·외부 전송·배포 권한은 별도로 현재 사용자의 지시를 따른다.

## 5. 검증 없이 완료 없음

검증 기준은 [공통 대조 기준](references/failure-modes-common.md)을 사용한다.

| 대상 | 대조 |
|---|---|
| 짧은 답변 | 출처·범위·조건·원문·사실/판정을 자체 점검. 파일이나 검수자 없음 |
| 남는 산출물·phase 마무리 | NOTES의 사실·검증 기록 ↔ 산출물 ↔ 지목된 원천을 대조. 가능한 경우 새 컨텍스트 검수자 1명, 최대 2라운드 |
| 외부 공유·의사결정 근거·SSOT·장애 보고 | 위 대조 + 사실 행 최소 3건(3건 미만이면 전부)을 원천에 표본 대조. 최대 3라운드. 미검증 목록 명시 |

- 검수자는 [검수 지시서](references/reviewer-instructions.md)를 읽고,
  PLAN·NOTES·STATE와 검수 대상의 절대 경로, 라운드, 해당 원천 위치를 받는다.
  검수자는 한 번에 1명만 사용하고, 지적 반영 후 재검수한다.
- 검수는 구현 기준이 된 확정 PLAN과 산출물을 비교한다. NOTES의 확정본 식별자로 PLAN 변경 여부를 확인하고,
  verify 결과·피드백보다 앞선 개정 또는 기준 완화를 발견하면 지적한다. 검수 도중 PLAN을 고쳐 통과시키지 않는다.
- 코드의 기능 검증은 적절한 테스트·실행으로 한다. 사실 대조가 기능 테스트를 대신하지 않는다.
- 검수자는 새 사실을 만들거나 원천 전체를 재탐색하지 않는다. 필요한 추가 수집 위치만 지적한다.
- 판정: `PASS`(Critical/Major 없음), `REWRITE`(근거는 충분하나 표현·범위 수정 필요),
  `RECOLLECT`(원천 추가 확인 필요). 결과와 지적·해소 여부는 NOTES의 검수 절에 기록한다.
- 같은 사실 ID(근거 없으면 주장 요지) + 같은 검증 기준으로 두 번 실패하면 해당 사실의 확정을 중단한다.
  라운드 상한에 도달해도 남은 문제를 숨기지 않고 미확정·후속 작업으로 남긴다.
- 서브에이전트를 쓸 수 없으면 작성 흐름을 멈추고 NOTES·산출물·기준만 다시 읽어 대조한다.
  검수 방식은 `독립 검수 아님 (자체 대조)`로 쓴다. 검수 에이전트 설치를 선행 조건으로 삼지 않는다.
- 사용자 보고에는 결과·핵심 근거·실행한 검증·미검증 한계를 필요한 만큼 담는다.
  매번 형식적인 카운트·등급 보고를 붙이지 않는다.

## 6. 기존 feature-workflow 명령과 하네스

기존 `start`·`resume`·`notes`·`verify` 호출에도 이 통합 규칙을 적용한다.
플러그인 명령은 이 스킬의 기본 기록·근거 규칙을 공통으로 적용한다.
단, 실행 중인 하네스의 쓰기 소유권·권한 게이트·상태 스키마는 우회하지 않는다.

- 유인 실행에서는 세션이 STATE를 갱신한다.
- `fw run` 무인 실행에서는 STATE는 하네스 소유이며 세션은 읽기 전용이다.
  검증 결과·충돌·필요한 정정은 NOTES와 하네스가 요구하는 출력에 남기고 하네스가 상태를 갱신하게 한다.
- 하네스의 `blocked`는 사용자 응답이 필요한 상태, `halted`는 운영 중단 상태로 구별한다.
  하네스 모드에서는 해당 하네스의 출력 계약을 따른다.
- 무인 실행·PR 모드를 임의로 켜지 않는다. 기존 안전 가드·신뢰 작성자·알림·중단 규칙을 유지한다.
- 실제 하네스·명령을 사용할 때는 [하네스 문서](../../harness/README.md)와 해당 스키마를 확인한다.
  하네스가 없더라도 PLAN·NOTES·STATE로 수동 진행할 수 있다.

별도 `grounded-work`가 함께 설치되어 있으면 근거 절차를 중첩 실행하지 않고 이 스킬의 NOTES 기반 기록으로 통합한다.

## 기본 적용 설정

플러그인 설치만으로 다른 저장소의 전역 지침을 수정하지 않는다.
매 대화의 진입점으로 고정하려면 사용하는 도구의 전역 지침에 이 스킬을 읽고 적용하도록 명시한다.
프로젝트 기본 지침으로 지정하려면 루트 AGENTS.md 또는 CLAUDE.md에 이 스킬 경로를 추가한다.
짧은 답변에도 전체 파일 기록이나 하네스 실행을 강제하지 않는다.

하네스의 내부 기계 상태 `INTERVIEW.json`과 실행 로그는 유지한다. 사람이 관리하는
계획·근거·검수 기록은 세 파일에 모으며, 새 하네스 검수 결과는 NOTES에 누적한다.
과거 `VERIFY.md`는 당시 원문으로 보존하며 새 검수 결과로 덮어쓰지 않는다.
