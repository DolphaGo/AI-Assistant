# Changelog

이 파일은 [Keep a Changelog](https://keepachangelog.com/) 간이형을 따른다. 과거 이력은
소급 작성하지 않는다(부정확한 기억 기반 재구성을 피하기 위함) — 이 항목부터 시작한다.

## [Unreleased]

### Added

- **`/feature-workflow:start` 가 "PR 을 잘게 나눌까요?" 를 묻는다**: 조각 PR(`review_split`)은
  기본 꺼짐인데 켜는 길이 STATE.json 직접 편집뿐이었다 — 문서에만 있고 아무것도 물어보지
  않으니 **사실상 영원히 꺼진 상태로 남는다.** 정작 가장 필요한 때(작업이 큰 때)가 사용자가
  설정을 떠올릴 여유가 가장 없는 때다.

  인터뷰 끝, 파일 생성 전에 묻는다. 그 시점에는 base 브랜치와 작업 규모가 이미 정해져 있어
  실제 브랜치 이름을 넣은 그림을 그릴 수 있다:

  ```
  feature/PROJ-123-1 ──PR──▶ ┐
  feature/PROJ-123-2 ──PR──▶ ├─ feature/PROJ-123 ──PR──▶ develop
  feature/PROJ-123-3 ──PR──▶ ┘
  ```

  내부 설정 이름(`review_split`)으로 묻지 않는다 — 사용자가 결정하는 것은 설정이 아니라
  리뷰를 어떻게 받을지다. phase 가 여러 개거나 한 phase 가 여러 관심사를 건드릴 것으로
  보이면 켜기를 추천하고 근거를 한 줄로 말한다. `branch_strategy: "current"` 를 골랐으면
  하네스가 시작 시점에 거부하는 조합이므로 **묻지 않고** 그 사실만 알린다(묻고 나서 안 된다고
  하지 않는다).

### Changed

- **PR 본문을 리뷰어 기준으로 다시 썼다**: 본문이 하네스의 내부 사정을 기준으로 짜여 있었다 —
  절 제목마다 그 값의 출처를 괄호로 설명했고("변경 요약(무인 세션 보고)", "커밋(main 대비
  실측)", "검증(이 조각이 통과한 명령)"), 조각 위치·분해 근거·파일별 증감·예산 실측이 정작
  세션이 쓴 설명보다 위에 있었다. 리뷰어에게는 전부 소음이다.

  본문에서 뺀 것과 그 이유: **커밋 목록·파일별 증감**은 GitHub 의 Commits / Files changed
  탭이 이미 보여주므로 처음부터 중복이었다. **조각 분해 근거**는 STATE·`fw doctor` 에,
  **예산 대비 실측**은 실행 로그에(리뷰어가 아니라 운영자용 신호다), **검증 명령**은 실행
  로그·STATE 에 남는다. 없앤 것이 아니라 자리를 옮겼다.

  남은 것은 셋뿐이다 — 이 PR 이 어디로 머지되는지 한 줄, 세션이 쓴 설명, 읽는 순서를 어디서
  보는지. 인라인 코멘트를 붙인 항목은 본문 목록에서도 빠진다(이유도 순서도 코드 위에 있다).

  통합 PR 본문도 같은 원칙으로 정리했다: 커밋 목록을 빼고(통합 PR 은 조각들의 합이라 그
  목록이 특히 길다) 조각 PR 링크만 남겼다 — GitHub 이 대신 보여줄 수 없고, "이미 리뷰가
  끝났으니 처음부터 다시 읽지 않아도 된다"는 이 PR 의 유일한 핵심 정보다.

- **세션이 쓰는 PR 설명에 지시를 만들었다**: `summary` 에는 아무 지시가 없어서(스키마에
  `summary: string` 뿐) 세션이 코드 조각·테스트 개수·"커밋 완료"를 한 덩어리로 쏟아냈다.
  이제 "무엇을 하는 변경인가 → 왜 필요한가 → 알아둘 것" 순서의 평문으로 쓰게 하고, 진행
  보고·코드 조각·파일 목록은 쓰지 말라고 명시한다(하네스가 이미 검증하거나 GitHub 이 이미
  보여주는 것들이다). 자기 작업을 보고하는 글이 아니라 남이 이해하게 돕는 글이어야 한다.

### Fixed

- **머지된 PR 로 재개할 때 하네스가 영구히 막히던 문제**: 재개 경로가 PR 상태를 보기 **전에**
  head 브랜치로 무조건 push 했다. **머지된 PR 의 head 브랜치는 사라지기 쉽다** — GHE 는 머지
  직후 모든 PR 에 "Delete branch" 버튼을 띄우고, 리포 설정으로 자동 삭제를 켜둔 곳도 있다.
  그 브랜치가 원격에 없으면 `--force-with-lease` 가 `stale info` 로 거부하고, 게이트가 예외로
  죽어 **머지를 끝내 감지하지 못한다.** `fw retry` 는 `phase.pr` 이 있으면 `in_review` 로
  되살리므로(중복 PR 방지) 재시도해도 같은 지점에서 다시 죽는 영구 루프였다. 조각 PR 만의
  문제가 아니라 `pr_mode` 로 중단된 워크플로우 전부가 복구 불가였다.

  동기화를 없애지 않고 **자리를 옮겼다**: 폴링 루프가 머지·닫힘을 걷어낸 직후, "PR 이 열려
  있다"가 확정된 지점에서 한 번만 push 한다. 사라진 브랜치에 push 하는 일이 구조적으로
  불가능해진다. push 실패를 삼키는 방식은 택하지 않았다 — 그러면 열린 PR 의 동기화 실패까지
  조용히 넘어가 "리뷰어가 낡은 코드를 보는데 하네스는 done 을 보고한다"(§25 D)가 돌아온다.

  뮤테이션이 함께 잡은 것: 동기화를 매 폴링마다 하면 PR 브랜치 push 로 **CI 가 계속
  재실행된다**(30초 폴링 × 며칠). "폴링이 여러 바퀴 돌아도 push 는 한 번" 을 테스트로 고정했다.

### Added

- **읽는 순서를 코드 위에 붙인다 (인라인 리뷰 코멘트)**: 읽는 순서가 PR 본문의 한 절이면 리뷰어가
  "cli.ts 193번째 줄 근처를 보라"를 읽고 Files changed 로 넘어가 그 줄을 직접 찾아야 했다 — 안내가
  코드에서 떨어져 있어 진입 비용이 그대로 남았다. 이제 본문에는 **파일 순서만** 남고, 각 파일을 왜
  봐야 하는지는 그 파일 변경 지점의 인라인 코멘트로 간다(순서는 흩어진 코멘트로 표현할 수 없고,
  위치는 목록으로 표현할 수 없다 — 역할을 나눈다).

  **앵커는 diff 에서만 뽑는다.** 세션이 쓴 줄 번호는 검증할 수 없는 추측이다. GHE 3.19 실측:
  diff 밖의 줄은 `422 line must be part of the diff` 이고, 코멘트를 리뷰 하나로 묶어 보내므로
  **앵커 하나만 틀리면 코멘트 전체가 거부된다**. 그래서 세션에게는 "어떤 파일을 왜 먼저 보라"만
  받고 줄 번호는 하네스가 `git diff -U0` 로 잰다. 줄을 추가한 첫 hunk 에 `RIGHT`, 삭제만 있는
  파일은 삭제된 줄에 `LEFT` 로 붙인다(둘 다 실측으로 통과 확인). `subject_type:"file"` 은 리뷰
  API 가 받지 않으므로(`Field is not defined on DraftPullRequestReviewComment`) 붙일 곳이 없는
  파일은 인라인을 포기하고 본문에 이유까지 남긴다.

  **정보가 사라지지 않는다.** 붙일 수 없는 항목은 본문에 전문이 남고, 붙이기가 실패하면 전문을
  일반 코멘트로 대신 남긴다. 인라인 코멘트 본문은 하네스 센티널로 시작한다 — 이 코멘트는
  `pulls/{n}/comments` 로 다시 읽히고 작성자가 신뢰 목록에 있는 사람이므로, 세션이 쓴 이유에
  `@fw` 가 섞이면 하네스가 자기 코멘트를 지시로 읽는 고리가 생긴다.

- **조각 PR (`review_split`) — 큰 phase 를 리뷰 가능한 크기로 나눈다**: phase 하나가 곧 PR 하나이면
  PR 이 리뷰할 수 없을 만큼 커진다(실측: `tamper-gap` 워크플로우 머지 15 files/+1934, 그중 워크플로우
  문서 기록 단독 +1061 — 부피의 절반 이상이 리뷰 대상이 아닌 인수인계 기록이었다).

  **토폴로지**: 조각 PR 은 base 브랜치가 아니라 **통합 브랜치**로 간다
  (`<통합브랜치>-N → <통합브랜치> → <base 브랜치>`). base 브랜치가 중간 상태를 볼 일이 없으므로
  조각이 그 자체로 완결일 필요가 없고, "인터페이스만 추가 / 구현 / 호출부 교체" 처럼 자연스럽게
  나눌 수 있다. 워크플로우 끝에 통합 PR 하나가 자동 생성되고, 그 본문에 조각 PR 링크와 "각 조각은
  이미 개별 리뷰를 통과했다" 는 사실이 담긴다.

  **분해**: phase 실행 **전에** 읽기 전용 세션이 조각 경계를 정한다. 실패·거부·"쪼갤 필요 없음" 은
  모두 원본 phase 를 그대로 실행하는 것으로 수렴하고(fail-open) 그 이유가 STATE·`fw doctor` 에
  남는다. 자동 재분해는 하지 않는다(무한 분해 루프 방지). 조각은 새 개념이 아니라 phase 로 편입되어
  세션·게이트·PR·머지 대기·이탈 감시 등 기존 방어를 그대로 받는다.

  **PR 본문의 리뷰 가이드**: 조각 위치 / 이 조각의 범위 / 리뷰 대상·기록용 파일 분리와 예산 실측 /
  읽는 순서 / 변경 요약 / 커밋 / 통과한 검증 명령. 하네스가 직접 잰 사실과 세션 주장을 구분해 담고,
  세션 출처 텍스트는 전부 마스킹을 거친다. 리뷰 대상/기록용 구분은 추측이 아니다 — 워크플로우
  디렉토리는 하네스가 아는 값이라 그 하위는 확정적으로 기록용이다.

  **안전장치**: 조각 브랜치를 파괴적으로 만들지 않는다(이름이 이미 쓰이고 있으면 소유권을 확인하고
  아니면 멈춘다 — 워크플로우 `wf` 의 조각 1 과 워크플로우 `wf-1` 의 통합 브랜치가 같은 ref 가 되는
  충돌이 실측으로 확인됐고, 이름 규칙으로는 막을 수 없다). 머지 후 통합 브랜치 전진은 **강제 없는
  fast-forward** 라 데이터 손실 경로가 없다. `pr_mode` 없이 켜거나 `branch_strategy: "current"` 와
  함께 켜면 시작을 거부한다.

  **하위호환**: 끄면(기본값) 주행 동작이 기존과 동일하다. 신규 STATE 필드는 전부 optional 이라
  기존 워크플로우의 STATE.json 이 그대로 로드된다(리포의 10개 워크플로우로 확인).

- **`fw init` 이 base 브랜치를 감지한다**: 예전에는 `main` 하드코딩이라 git flow 리포
  (`develop ← feature/*`)에서 PR 이 통합 대상이 아닌 곳으로 갔다. `develop` 우선 →
  `origin/HEAD` → `main` 폴백 순으로 감지하고 **감지 근거를 항상 출력**한다. `origin/HEAD` 가
  가리키는 브랜치의 실존까지 확인해, 원격 rename 후 남는 dangling 심볼릭 ref 에서 존재하지 않는
  브랜치를 base 로 확정하지 않는다. 폴백 사유를 `not-a-repo`/`dangling-origin-head`/`no-signal`
  로 구분해 인프라 오류에 원인과 무관한 교정 지시가 나가지 않게 했다.

- **`fw doctor` 에 `[조각 분해]` 절**: 켜짐 여부·예산·통합 브랜치·조각 진행률·분해를 건너뛴 이유·
  `base_branch` 와 리포 관례 불일치·통합 PR URL 을 보여준다. 판정(exit code)에는 넣지 않는다.

### Fixed

- **PR fix 세션이 코멘트의 지적 일부만 반영하고 조용히 넘기던 결함(issue #4)**: 하네스의 fix
  검증은 "커밋이 있는가 + 게이트 통과"뿐이어서, 두 문장짜리 `@fw` 코멘트의 첫 문장만 반영한 세션이
  `done` 으로 확정됐다(실측: PR 전제를 뒤집는 두 번째 지적이 미반영된 채 "반영했습니다" 답글). 이슈
  제안 1~4 를 모두 반영했다.
  1. 세션 결과에 **`addressed`** 배열 추가 — 코멘트에서 추출한 개별 요구/지적 항목과 각각의 상태
     `applied / already_applied / declined / not_applicable` + 근거(evidence). fix 프롬프트에 항목
     추출·항목별 보고 규칙을 넣었다("항목이 하나라도 빠지면 done 이 아니다"). 신뢰 경계 밖 값이라
     개수(30)·길이(300자) 상한을 두고, 초과분은 declined 표식 항목으로 드러낸다(조용히 버리지 않음).
  2. 하네스는 done/already_applied 인데 `addressed` 가 비어 있으면 새 verdict reason
     **`comment_items_unreported`** 로 회송한다(커밋이 있어도). 항목 수는 자연어라 셀 수 없으므로
     내용은 검증하지 않고 "항목 추출 자체를 안 함"만 잡는다. 검사 순서는 브랜치 이탈 → 항목 보고 →
     커밋 검증.
  3. `✅` 답글에 항목별 결과를 한 줄씩 싣는다(`✅ 반영함 / ⏭ 이미 반영됨 / ❌ 반영 안 함 / ➖ 해당
     없음 — 항목: 근거`). item/evidence 는 maskSecrets + 한 줄 접기 + 절단을 거친다.
  4. `declined` 가 하나라도 있으면 코멘트 작성자를 `@멘션` 해 명시적 확인을 요청한다(GitHub 로그인
     형태가 아닌 author 는 멘션하지 않음). `addressed` 는 STATE `phase.sessions[].addressed` 에도
     남아 감사 추적 원본이 된다(선택 필드 — 기존 STATE 호환).
- **PR fix 세션의 no-op 보고가 FAILED 로 떨어지던 결함(issue #3)**: `@fw` 코멘트를 처리하는 fix
  세션이 "이미 반영되어 있어 추가 커밋 불필요"라고 정직하게 보고할 어휘가 없어 `done + commits:[]`
  → `no_commits` 회송 → 워크플로우 전체 FAILED 로 이어졌다(실측 2회: 겹치는 리뷰 코멘트를 앞
  세션이 함께 정리한 경우, 커밋·push 후 handled 기록 전 중단 → 재개). 세 갈래로 고쳤다.
  1. 세션 결과 status 에 **`already_applied`** 추가 — commits 에 반영이 담긴 **기존 커밋 SHA**(근거)를
     넣는다. 하네스는 `verifyAlreadyAppliedCommits` 로 SHA 실존 · PR 브랜치(push 되는 ref) 도달성 ·
     **base_branch 미포함**(최초 커밋 등을 근거로 대는 no-op 세탁 차단)을 검증한 뒤에만 handled 로
     확정하고 정상 진행한다. 검증 실패는 새 verdict reason `already_applied_unverified` 로 회송된다.
     배치 전체가 already_applied 면 위조 가드·verify 게이트를 건너뛴다(변경이 없다). 답글은
     `✅ <key> 이미 반영됨 (추가 커밋 없음)` + 근거 커밋. phase 세션이 이 값을 내면 기존 신규 커밋
     검증에 걸려 회송된다(fix 전용).
  2. `phase.pr.in_flight_comment_keys` 마커 — fix 세션을 띄우기 직전에 코멘트 키를 STATE 에 기록하고
     handled 확정 시 지운다. 재개 시 남아 있는 키의 세션에는 "직전 실행이 처리하던 중 중단됐다 —
     `git log` 로 이미 반영됐는지 먼저 확인하라"는 안내가 프롬프트에 붙는다(`FixPromptInput.
     interruptedPreviously`). 기존 STATE 는 필드 없음 == 빈 배열로 로드된다.
  3. `fw retry <phase>` 가 `phase.pr` 이 있는 phase 를 `pending` 이 아니라 **`in_review`** 로 되살린다
     (answerQuestion 의 B-2 와 대칭) — 이전에는 재개 시 phase 세션이 새로 떠서 새 PR 을 만들 수 있었다.
  - 미반영: 이슈 제안 3(같은 폴링의 여러 `@fw` 코멘트를 한 세션에 묶기)은 "1건씩 독립 실행" 설계
    (부분 blocked 시 배치 전체가 미처리로 남는 실전 결함의 해법)와 충돌하므로 이번 범위에서 제외했다.
    겹치는 코멘트 문제는 1 로 해소된다.

### Changed

- **격리 브랜치 접두 통일(§68)**: 하네스 자동 격리 브랜치가 `fw/<workflow>` → `feature/<workflow>`
  로 바뀌었다(사용자 결정 — start 가 만드는 토픽 브랜치와 네임스페이스 통일). 이름 규칙은
  `branch.ts` 의 `isolationBranchName()` 한 곳으로 모았다(생성과 머지 후 재생성이 항상 같은
  이름을 계산하도록). **push 허용 정책이 함께 정밀화됐다**: feature/ 접두를 통째로 열면 세션이
  사람 소유 feature 브랜치에 push 할 수 있으므로, 접두 허용은 하네스 전용 `fw/`(phase PR 헤드
  `fw/phase-<id>`)에만 남기고 작업 브랜치는 `policy.workBranch` **정확 일치**로만 허용한다
  (orchestrator/prloop 가 applyBranchStrategy 확정값을 policyFor 로 스레딩; 미주입 경로는 기존
  fw/ 접두만 — fail-closed). **하위호환**: 진행 중이던 `fw/<workflow>` 브랜치는 isolate 가
  "base 가 아닌 브랜치"로 보고 그대로 작업 브랜치로 삼으므로 재개는 깨지지 않는다 — 다만 머지
  후 격리 브랜치 재생성(§26 M5)은 이름 불일치로 건너뛰어 누적 PR 로 퇴화할 수 있다(로그로 안내됨).
- `preflight()` 의 워킹트리 상태 확인이 `git status --porcelain(-z)`(v1)에서
  `git status --porcelain=v2 -z`(v2)로 바뀌었다. v2 는 레코드 타입(`1`/`2`/`u`/`?`/`!`)이
  필드 개수를 스스로 서술하므로, 이제까지 조용히 통과되던 기형·미인식 레코드(예: rename/copy
  레코드의 OLD 경로 필드 누락, 인식할 수 없는 상태 코드, 병합충돌(`u`) 레코드의 필드 구조
  이상)를 **정지시킨다**(fail-closed) — 이전에는 이런 입력을 만나면 조용히 다음 레코드로
  넘어가거나(v1 -z 의 구조적 한계) 무시했다.
- 이 하네스는 이제 `git 2.11+`(2016, `--porcelain=v2` 최소 요구 버전)을 전제한다. 그보다
  낮은 버전에서는 `git status` 호출 자체가 실패하며, 오류 메시지에 감지된 git 버전과 함께
  "이 하네스는 2.11+ 필요"라는 힌트가 덧붙는다(버전 문자열을 파싱할 수 있을 때만).

### Added

- **`fw <cmd>` 의 docs/ 접두 자동 해석(§69)**: 모든 명령의 `<dir>` 인자에 워크플로우 이름만
  써도 된다 — `fw run writing-training` == `fw run docs/writing-training`. 단독 이름이면
  `docs/<이름>` 으로 해석하되, 현재 디렉토리에 `<이름>/STATE.json` 이 있으면 그쪽을
  우선한다(STATE.json 존재 기준이라 동명의 무관한 디렉토리에 가로채이지 않는다). 경로
  구분자/절대경로/`.`·`..` 는 기존 그대로(하위호환). `fw init <이름>` 도 docs/<이름> 에
  생성한다 — 만드는 곳과 찾는 곳이 항상 같다.
- **start 단계 작업 위치 합의 + 이슈/티켓 컨텍스트(§68)**: `/feature-workflow:start` 가
  본작업 인터뷰 전에 (1) 인자가 이슈 트래커 URL·티켓 ID 패턴이면 **현재 세션에 읽을 도구가
  있는 경우에만**(이슈 트래커 MCP, WebFetch 등 — 특정 벤더 비종속, 없으면 붙여넣기 요청)
  내용을 가져와 인터뷰 추천 답안 재료로 쓰고, (2) 작업 위치를 새 브랜치 분기(리포 관례
  감지 — `develop` 존재 시 git flow 로 보고 base 추천, `feature/*` prefix 추천) / 현재
  브랜치(`branch_strategy: "current"`) / 하네스 자동 격리 중에서 합의한다. prefix·base 는
  추천만 하고 강제하지 않는다(브랜치 전략 사용자 위임 원칙). 새 브랜치 분기는 **원격 동기화가
  선행 조건** — `git fetch origin <base>` 후 `origin/<base>` 기준 `--no-track` 분기(로컬 base
  가 뒤처져 있어도 최신 기준, upstream 오염 없음 — §41 과 같은 축). 브랜치 이름은
  `feature/<작업 이름>` 으로 **작업 이름(=docs 디렉토리명=STATE `workflow`)과 정확히 같은
  문자열**을 쓴다 — 하네스의 머지 후 브랜치 최신화(§26 M5)가 `feature/<workflow>` 정확 일치로
  소유를 판정하므로, 이름이 어긋나면 squash 머지 환경에서 다음 phase PR 에 이전 phase diff 가
  중복된다. 이 일치는 사용자가 아니라 start 스킬이 지키는 규칙이다.
- **세션 스트림 무활동 타임아웃(§65)**: 모든 세션(phase/fix/verify/합의/인터뷰)이 스트림
  메시지 없이 20분을 넘기면 세션을 실패 처리하고 재시도 루프에 태운다. VPN/네트워크 단절
  시 프로세스는 살아 있는 채 무한 대기하던 클래스(실측 16시간)를 막는다. 메시지가 하나라도
  오면 타이머가 리셋되므로 총 세션 길이는 제한하지 않는다.
- 위 정지 상황을 만났을 때 할 일: 오류 메시지가 `위조 탐지를 신뢰할 수 없는 상태라 안전하게
  정지합니다` 문구와 함께 스네이크 케이스 카테고리 토큰(예: `xy_invalid`, `mode_invalid`,
  `stream_ended`, `mid_field_missing` 등 9종 중 하나) + 문제가 된 레코드 원문(그리고
  `mid_field_missing` 인 경우 "다음 레코드 원문:" 이라는 두 번째 증거)을 함께 담는다.
  카테고리와 원문을 확인해 실제 git 출력이 예상과 다른 이유(예: git 버전, 사용자 지정 git
  설정)를 파악한 뒤 `fw retry` 로 재개하면 된다.
