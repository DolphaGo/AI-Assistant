# Feature Workflow

복잡한 작업 (대규모 마이그레이션, 멀티모듈 리팩토링, 다단계 피처 구현 등) 을 일관된 방식으로 끝까지 끌고 가는 워크플로우. 사용자가 한 번 요청하면 끝까지 같은 패턴으로 진행되며, 세션이 끊겨도 다음 세션이 PLAN/STATE/NOTES 문서만 읽고 이어받을 수 있다.

## 언제 발동되나

다음 신호 중 하나라도 있으면 즉시 이 skill 을 따른다:

- "마이그레이션 / 이관 / 멀티모듈화 / 구조 변경 / 리팩토링" 같은 키워드 + 작업 범위가 한 PR 이상
- 사용자가 "계획을 짜고 차근차근" / "단계별로" / "세세히 커밋" / "핸드오프" 같은 표현
- "세션 끊겨도 다음 AI 가 이어받게" / "현황판" 같은 지속성 요구
- 명백히 큰 작업 (>5 파일 이상 변경, 또는 여러 의존 단계)

작은 작업(단일 파일 수정, 버그 핫픽스)에는 발동하지 않는다.

## 핵심 원칙

1. **불확실하면 묻는다** — 모호한 부분을 임의로 결정하지 않고 `현재 환경의 사용자 질문 수단`/`request_user_input`/직접 질문 등 현재 환경의 사용자 질문 수단 으로 사용자에게 확인. "Recommended" 옵션을 제시하되 강요하지 않음. **묻기 전에 기존 PLAN §핵심 결정·§용어를 먼저 읽는다** — 문서를 읽으면 답이 나오는 걸 묻지 말고, 이미 정해진 것과 충돌하는지를 근거로 캐묻는다(프리스타일 질문 금지).
2. **결정 충돌이 발견되면 즉시 멈추고 묻는다** — phase 실행 도중에라도 PLAN 의 기존 결정과 어긋나는 상황(예: 합의된 모듈 구조와 다른 코드 발견, 두 결정이 서로 모순, 새 제약이 등장해 기존 계획이 깨짐)을 만나면 그 자리에서 작업을 멈추고 사용자에게 확인. 임의로 절충안을 만들어 진행하지 말 것. 확인 후 결정은 PLAN §핵심 결정 사항 에 추가.
3. **결정은 그 자리에서 기록하고, 지우지 않는다** — 짧은 채팅 결정도 즉시(나중에 몰아서가 아니라) PLAN §핵심 결정 표에 남긴다. **뒤집힌 결정은 삭제하지 말고 `superseded by D<n>` 으로 표시한다** — 덮어쓰면 "왜 이렇게 했지" 의 답이 사라지고, 다음 세션이 폐기된 결정을 되살리는 사고가 난다.
4. **작업 단위는 작게** — 한 phase 는 commit 3~6개 분량. 큰 phase 는 하위 단계로 쪼갠다.
5. **매 phase 끝에 STATE·NOTES 갱신** — 절대 빼먹지 않는다. STATE 의 phase status·next_steps(다음 작업 단계)는 항상 최신으로, NOTES 에는 이번 phase 의 사람용 서사를 남긴다.
6. **검증은 명령으로** — `./gradlew build` 같은 검증 명령을 phase 마다 실행하고 결과를 NOTES 에 기록.

## 산출물 3종과 STATE.json 갱신 (유인/무인 공통)

워크플로우는 **하네스를 쓰든 안 쓰든 항상 3개 파일**을 갖는다. 모드에 따라 상태를
다른 파일에 적으면 모드를 왕복할 때(유인으로 시작 → `fw run` 무인 → 다시 유인) 서로를
못 읽으므로, 한 가지 규칙으로 통일한다:

| 파일 | 담는 것 |
|---|---|
| `PLAN.md` | 변하지 않는 마스터 플랜 · **§핵심 결정 표(ID·상태·근거)** · **§용어** |
| `NOTES.md` | 이관 맵 · 리스크 · 트러블슈팅 · 결정 배경 (**사람용 서사만**) |
| `STATE.json` | **phase 목록·상태·시도·PR·phase 별 `next_steps`(다음 작업 단계) — 기계 사실의 유일한 진실** |

**PLAN 의 phase 표와 STATE.json 의 `phases` 는 항상 같은 목록이어야 한다** (제목·개수·순서).
STATE 는 거기에 상태·시도·PR·next_steps 를 얹을 뿐이다. **워크플로우 도중 phase 가 새로 생기면
STATE 에만 추가하지 말고 PLAN 표에도 같이 추가한다** — 한쪽만 늘리면 PLAN 은 초기 계획에
멈춘 채 STATE 만 자라서, 나중에 PLAN 을 읽는 사람이 실제로 무슨 일이 있었는지 알 수 없게 된다
(실제로 구 PROGRESS 체계에서 이 격차가 났고 2026-08-27 이관 때 5건을 소급 동기화해야 했다).
구 번호가 0 부터인 워크플로우는 `id` 가 1 부터라 1 만큼 어긋나므로, PLAN 표에 대응 관계를 적어둔다.

**phase 진행 상태 표를 NOTES.md 에 적지 않는다.** 현황은 `fw status docs/<workflow>` 로
본다 (하네스로 실행하지 않아도 이 명령은 STATE.json 만 읽어 표로 그려준다).

### STATE.json 을 누가 갱신하나 — 모드별로 다르다

- **유인 모드(`/feature-workflow:resume` 등 사람이 세션을 운전할 때):** 하네스가 없으니
  **세션이 직접 갱신한다.** phase 를 끝냈으면 STATE.json 의 해당 phase `status` 를
  `"done"` 으로 바꾸고, 다음 phase 의 `next_steps`(상세 작업 단계)를 채운 뒤 그 변경도
  커밋하라. 이걸 빼먹으면 나중에 `fw run` 이 이미 끝낸 phase 를 처음부터 다시 실행하거나
  다음 세션이 작업 단계 없이 시작하게 된다. 편집 시 JSON 유효성을 깨지 않도록 주의(스키마가
  strict 이므로 오타 키는 로드 거부된다).
- **무인 모드(`fw run` 이 띄운 세션):** **STATE.json 은 하네스 소유 — 세션은 읽기 전용.**
  절대 수정하지 마라(권한 게이트가 쓰기를 차단한다). 하네스가 검증 판정 후 직접 기록한다.

## 무인 실행 (fw 하네스)

이 워크플로우는 `fw` 하네스(plugins/feature-workflow/harness)로 무인 실행될 수 있다.
무인 세션으로 실행 중일 때는 다음 규약을 따른다:

1. **BLOCKED 규약** — 물을 사람이 없다. "불확실하면 묻는다"는 "묻는 대신
   status=blocked + question 을 구조화 출력으로 반환하고 종료"로 치환된다.
   임의 결정·절충 진행은 유인/무인 모두 금지.
2. **STATE.json 쓰기 금지** — 무인 세션에서는 하네스가 단일 작성자다(위 표 참조).
   사람용 현황은 NOTES.md 에 기록한다.
3. **검증 최종 판정은 하네스가 한다** — 세션이 검증 명령을 실행해 봐도 되지만,
   phase 완료 판정은 하네스가 검증 명령을 직접 재실행해 내린다. 따라서 verify 명령은
   실패 시 반드시 non-zero exit 해야 한다 (`true`/`echo`/`|| true`/`| tee` 금지) —
   이는 산문 규칙에 그치지 않는다. `fw run` 이 시작 시점에 이 패턴을 정적으로 검사해
   위반하면 세션을 한 번도 띄우지 않고 즉시 거부한다(§26 I5 잔여 승격). `fw doctor <dir>` 로
   전체 phase 의 검증 명령을 미리 점검할 수 있다.
4. **브랜치 안전 — 프리플라이트 + `branch_strategy`(§19)** — `fw run` 시작 직후 하네스가
   repo_root·git 저장소 여부·워킹트리 청결·(pr_mode 면) `gh auth status` 를 확인한다.
   문제가 있으면 세션을 한 번도 띄우지 않고 FAILED + 알림으로 정지한다(해결 방법이 메시지에
   포함된다). 통과하면 STATE.json 의 `branch_strategy` 로 어느 브랜치에서 작업할지 정한다:
   - `"isolate"`(기본, 권장) — 현재 브랜치가 `base_branch` 와 같으면 하네스가 `feature/<workflow>`
     브랜치를 만들어(이미 있으면 체크아웃만) 세션을 그 위에서 돌린다. **main 에서 `fw run` 을
     그냥 돌려도 main 에 커밋이 쌓이지 않는다.** 이미 `base_branch` 가 아닌 브랜치에 있으면
     (예: start 단계에서 분기해 둔 `feature/<티켓ID>`) **그 브랜치를 그대로 작업 브랜치로
     삼아 이탈 감시한다** — 별도 설정이 필요 없다.
   - `"current"` — 현재 체크아웃된 브랜치에서 그대로 작업한다(사용자가 이미 토픽 브랜치를
     만들어둔 경우). `base_branch` 위에 있으면 경고 로그만 남기고 그대로 진행한다 — **이
     경우에는 정말로 그 브랜치에 직접 커밋이 쌓인다.**
   - `"require-topic"` — `base_branch` 위에서 실행하면 세션을 띄우지 않고 즉시 거부한다.
     토픽 브랜치를 직접 만들거나 `branch_strategy` 를 `isolate` 로 바꿔야 진행된다.
   `STATE.json` 작성 시(2단계) `templates/STATE.json` 의 기본값(`"isolate"`)을 그대로 두면
   대개 충분하다 — 사용자가 이미 만든 브랜치에서 돌리고 싶을 때만 `"current"` 로 바꾼다.
5. **PR 모드(v2)** — STATE.json 의 `pr_mode: true` + `allow_push: true` 면 phase 검증 통과 후
   PR 을 만들고 리뷰 왕복을 자율로 돈다. 리뷰어가 하네스에게 수정을 요청할 때는 코멘트에
   **`@fw` 또는 `/fw fix` 마커**를 붙여야 한다 — 마커 없는 코멘트(팀원끼리의 대화)는
   하네스가 읽지 않는다. approve 되면 하네스는 정지하고 **머지는 사람이** 한다.
   **PR 모드를 쓰려면 STATE.json 의 `trusted_comment_authors` 에 리뷰어 로그인을 반드시 넣어야
   한다** — 마커는 "나에게 한 말인가"만 정하고 "말할 자격이 있는가"는 정하지 않으므로, 이 목록에
   없는 작성자의 트리거 코멘트는 fail-closed 로 무시된다(빈 배열이면 아무도 신뢰하지 않는다).
6. **동시 실행 가드** — `fw run` 은 시작할 때 `docs/<workflow>/.fw.lock` 에 PID+시작시각을
   기록해 잡고, 종료(정상/크래시/Ctrl-C 무관)하면 해제한다. 이미 살아있는 `fw run` 이
   같은 워크플로우를 잡고 있으면 두 번째 `fw run` 은 거부된다(같은 STATE.json 을 두
   프로세스가 번갈아 덮어써 phase 상태가 뒤집히는 사고를 막기 위함). **`.fw.lock` 은
   실행 중에만 존재하는 프로세스 락이라 커밋 대상이 아니다 — 리포 루트 `.gitignore` 에
   이미 등록돼 있다.** `fw status`/`fw answer`/`fw retry`/`fw init` 은 락과 무관하게
   항상 동작한다(관측·개입을 막지 않음). 다만 `fw answer`/`fw retry` 는 실행 중인
   워크플로우에 개입할 때 STATE.json 을 같이 건드리게 되므로, 살아있는 락이 감지되면
   경고만 출력하고 진행한다(차단하지 않음 — 의도적 개입일 수 있다).
7. **관측 — 실행 로그 + `fw log`(§20)** — `fw run` 은 `docs/<workflow>/logs/run-<타임스탬프>.log`
   에 하네스 실행 로그(콘솔에 찍히는 것과 동일한 내용, `[HH:mm:ss]` 접두)를 append 하고, 종료
   시 콘솔에 그 경로를 알려준다. 밤새 무인으로 돌린 뒤에는 `fw log docs/<workflow>` 로
   STATE.json 요약(phase별 상태·시도·비용·PR) + phase 별 세션 이력(시간순) + BLOCKED 질문 +
   최근 run 로그 파일 목록을 한 화면에서 확인한다. `--last N` 을 주면 가장 최근 run 로그
   파일의 마지막 N 줄도 함께 보여준다. **`docs/<workflow>/logs/` 는 커밋 대상이 아니다** —
   verify 명령 출력(게이트 로그)과 run 로그 모두 토큰/시크릿이 무마스킹으로 섞일 수 있어
   리포 루트 `.gitignore` 에 `docs/*/logs/` 로 등록돼 있다. 이미 커밋된 로그가 있다면(과거
   실수) 지우지 말고 그대로 두되, 새 워크플로우에서 같은 실수를 반복하지 않는다.
8. **멈출 수단 — 상한과 킬 스위치(§27)** — 무인 주행의 전제는 "언제든 멈출 수 있다" 다.
   - **`fw stop docs/<workflow>`** — `STOP` 파일을 만들어 **다음 체크포인트에서** 정지시킨다.
     돌고 있는 세션을 죽이지 않으므로 커밋이 반쯤 된 상태가 남지 않는다. 시그널이 아니라
     파일인 이유: `nohup` 으로 띄운 밤샘 실행은 PID 를 모르고, 파일은 프로세스가 죽어도
     의도가 남는다. `fw run` 이 시작 시 이 파일을 **소비(삭제)** 하므로 따로 지울 필요 없다.
   - **STATE 의 `max_cost_usd` / `max_runtime_ms`** — 누적 세션 비용과 이 실행의 벽시계 시간
     상한. 초과하면 정지한다. **미설정(기본)이면 무제한** — 밤새 돌릴 때는 채우는 것을 권한다.
   - **`halted` 는 `blocked` 와 다르다.** blocked 는 **사람의 답변이 필요**(`fw answer`),
     halted 는 **그냥 이어서 `fw run` 하면 재개**된다(운영자/상한이 멈춘 것). `fw status`·
     `fw log`·`fw doctor` 가 `⏸` 와 정지 사유를 보여준다.
   - **`docs/<workflow>/STOP` 은 커밋 대상이 아니다** — `.gitignore` 에 `docs/*/STOP` 로 등록됨.
9. **알림은 사라지지 않는다(§27 O4)** — BLOCKED/완료/FAILED 알림은 **플랫폼 무관하게 stderr
   배너**로 항상 찍히고, 그 위에 macOS `osascript` / Linux `notify-send` 를 얹는다. 예전에는
   macOS 가 아니면 조용히 사라졌다.
10. **권한 감사 로그(§27 O1)** — 세션의 도구 사용 허가/거부가 실행 로그에 남는다. 거부는
   전문(`🔒 DENY Bash: ... — 사유`), 허용은 세션 종료 시 요약(`🔓 ALLOW 요약: Bash×34, Edit×12`).
   로그에 토큰이 섞이지 않도록 GitHub 토큰·`Authorization:`·API 키는 마스킹된다. **밤새 무엇이
   실행됐는지 사후에 재구성할 수 있어야** 사고가 났을 때 범위를 좁힐 수 있다.
11. **PLAN 의 결정·용어가 세션에 주입된다(§28)** — 하네스가 PLAN.md 의 §핵심 결정 사항·§용어
   절을 파싱해 **무인 세션 프롬프트에 그대로 박아 넣고**, 작업 시작 전 그것과 충돌하는지
   점검하라고 지시한다. "PLAN 을 읽어라" 는 지시도 유지되지만 그것에만 의존하지 않는다 —
   **그래서 §핵심 결정과 §용어는 산문이 아니라 표로 써야 한다**(위 2단계 참조).
12. **샌드박스 — SDK 네이티브 실행 격리(§37 T1, 옵트인)** — 위 "권한 감사 로그"(§27 O1)의
   `canUseTool` 은 세션이 **요청**한 도구 호출을 검사할 뿐이다. `npm run <script>` 처럼
   `package.json` 안의 셸 문자열을 실제로 **실행**하는 경로는 그 검사 지점을 거치지 않는다 —
   `npm run typecheck --prefix /tmp/evil` 로 다른 디렉토리의 임의 코드를 실행하는 것이 실제로
   성립했다(§36 C-1). 요청 검사와 실행 차단은 다른 것이다: 권한 검사는 하네스가 **본 문자열**을
   판정하고, 샌드박스는 **커널 수준에서 실행 자체**를 막아 이 축을 통째로 덮는다.
   `STATE.json` 의 `sandbox.enabled: true` 로 옵트인하면(기본은 비활성 — 미설정 시 기존 동작과
   완전히 동일) `@anthropic-ai/claude-agent-sdk` 의 네이티브 샌드박스(macOS Seatbelt/Linux
   bubblewrap/Windows 네이티브)가 세션 실행을 격리한다. `failIfUnavailable` 은 사용자가 뭘
   넣든 항상 `true` 로 강제된다(샌드박스 없이 조용히 도는 것이 최악이므로). `fw status`/
   `fw doctor` 가 켜짐 여부를 보여주고, 꺼짐은 문제로 만들지 않는다(옵트인이 기본값). 세부
   설정(`network`/`filesystem`/`credentials`)과 제안 프로파일은 `harness/README.md` 의
   "샌드박스" 절 참조 — **아직 실전 검증되지 않았다.**

## 5 단계 워크플로우

각 단계마다 어떤 산출물을 만들어야 하는지 명시한다.

### 1단계: Brainstorm (요구사항 명확화)

**목적:** 사용자의 첫 요청을 명확한 사양으로 변환.

**해야 할 일:**
- **먼저 기존 문서에 앵커링한다** — 이어받는 워크플로우면 `docs/<workflow>/PLAN.md` 의
  §핵심 결정·§용어를 읽는다. 새 워크플로우라도 리포의 CLAUDE.md·기존 워크플로우 PLAN 을
  훑어 이미 정해진 관례를 파악한다. **문서를 읽으면 답이 나오는 것은 묻지 않는다.**
- **이슈/티켓이 주어졌으면 컨텍스트로 삼는다** — 사용자 요청에 이슈 트래커 URL·티켓 ID
  패턴이 있으면, 현재 세션에 그걸 읽을 수 있는 도구가 있는 경우(이슈 트래커 MCP, 웹/이슈 읽기 도구
  등) 제목·설명·코멘트를 가져와 목표·모호점 질문의 추천 답안 재료로 쓴다. **특정 벤더에
  종속되지 않는다** — 도구가 없으면 내용 붙여넣기를 요청하고 진행한다(막지 않는다).
  티켓 링크는 PLAN.md 에 남긴다.
- **작업 위치(브랜치)를 먼저 합의한다** — 새 브랜치 분기 / 현재 브랜치 / 하네스 자동 격리
  중 선택 (`/feature-workflow:start` 3번 참조). prefix·base 는 리포 관례(예: `develop` 존재
  → git flow, 기존 `feature/*` prefix)를 감지해 **추천만** 하고 강제하지 않는다.
  새 브랜치를 분기할 때는 **원격과 로컬 일치가 선행 조건** — `git fetch origin <base>` 후
  `origin/<base>` 기준으로 `--no-track` 분기한다(로컬 base 가 뒤처진 채 분기하면 시작부터
  stale). 원격이 없으면 사용자에게 알리고 로컬 base 기준 진행을 확인받는다.
- **PR 을 잘게 나눌지 묻는다** — 인터뷰 끝에 브랜치 그림(조각 PR → 통합 브랜치 → base)을
  보여주며 "PR 을 잘게 나눌까요?" 를 묻고, 작업 규모를 근거로 추천을 붙인다
  (`/feature-workflow:start` 5번 참조). **묻지 않으면 사실상 영원히 꺼진 상태로 남는다** —
  STATE.json 을 직접 열어 고치는 것 말고는 켜는 길이 없고, 정작 가장 필요한 때(작업이 큰 때)가
  설정을 떠올릴 여유가 가장 없는 때다. `branch_strategy: "current"` 를 골랐으면 쓸 수 없으니
  묻지 말고 그 사실만 알린다.
- 사용자 요청에서 모호한 부분을 식별 — 특히 **기존 결정과 충돌하는 지점**을 찾는다
  ("D3 은 X 라고 정했는데 이번 요청은 Y 를 함의합니다 — D3 을 뒤집는 겁니까?")
- `현재 환경의 사용자 질문 수단`/`request_user_input`/직접 질문 등 현재 환경의 사용자 질문 수단 으로 1~3개 핵심 질문 (한 번에 4개 이하). 모든 질문에 **추천 답안을
  동봉**해 사용자가 백지에서 시작하지 않고 방향만 틀 수 있게 한다.
- 참조 프로젝트/예시가 있으면 구조 파악
- **해소된 결정은 그 자리에서 PLAN §핵심 결정 표에 적는다** — 인터뷰가 끝난 뒤 몰아서
  쓰지 않는다. 중간에 세션이 끊겨도 결정이 남아야 한다.
- 결정된 사양을 텍스트로 정리해서 사용자 확인

**산출물:** 명확한 사양 (사용자 확인 받음)

**함정:**
- 사용자가 답하지 않은 부분을 임의로 진행하지 말 것
- 한꺼번에 너무 많이 묻지 말 것 — 핵심부터

### 2단계: Plan (마스터 플랜 작성)

**목적:** 모든 단계를 미리 그려서 PR 단위로 쪼갠다.

**해야 할 일:**
1. `docs/<workflow-name>/` 디렉토리 생성
2. `PLAN.md` 작성 — 변하지 않는 마스터 플랜
   - Goal (1문장)
   - Architecture (2~3문장)
   - 모듈/파일 구조 (목표)
   - 의존 그래프
   - Phase 별 PR 단위 작업 순서 표
   - **§핵심 결정 사항 — 표로 쓴다** (아래 형식 참조). 하네스가 이 절을 파싱해 무인 세션
     프롬프트에 그대로 주입하므로, 산문이 아니라 표여야 한다.
   - **§용어 — 표로 쓴다** (아래 형식 참조). 여러 세션에 걸친 워크플로우는 용어가 갈리기
     쉽고, 갈린 용어는 코드 부채가 된다(실례: `topic` → `isolate` 이름 변경 때문에
     하위호환 alias 를 영구히 안고 감).

**§핵심 결정 사항 형식:**

| ID | 결정 | 근거 | 상태 | 날짜 |
|----|------|------|------|------|
| D1 | 브랜치 전략은 사용자에게 위임 | 강제하면 기존 워크플로와 충돌 | accepted | 2026-08-26 |
| D2 | 레거시 문서 자동 변환 금지 | 기존 문서 손상 위험 | superseded by D7 | 2026-08-26 |
| D7 | 레거시를 전면 이관 | 두 체계 혼재 비용이 더 큼 | accepted | 2026-08-27 |

상태값: `proposed` | `accepted` | `superseded by D<n>`. **행을 지우거나 덮어쓰지 않는다.**

**§용어 형식:**

| 용어 | 정의 | 쓰지 않는 말 |
|------|------|-------------|
| isolate | 하네스가 `feature/<workflow>` 브랜치를 만들어 격리 | ~~topic~~ (구 이름) |

"쓰지 않는 말" 열이 드리프트 방지 장치다 — 폐기된 용어를 남겨 다음 세션이 되살리지 않게 한다.
3. `NOTES.md` 작성 — 사람용 진행 메모.
   **phase 상태 표는 쓰지 않는다** — 그건 STATE.json 이 진실이고 현황은 `fw status` 로 본다
   - 모듈/파일 이관 맵
   - 알려진 리스크
   - 트러블슈팅 메모 / 결정 배경
4. `STATE.json` 작성 — 하네스(fw)용 기계 상태 (PLAN 의 phase 표와 동일한 phases 배열).
   **phase 별 `next_steps` 를 PLAN 의 해당 phase 작업 단계(상세 커밋 단위 목록)로 채운다** —
   다음 세션이 이어받을 때 참고하는 자리이므로 비워두지 않는다.
   **`branch_strategy` 는 기본값 `"isolate"` 를 그대로 둔다** (base_branch 에서 실행되면 하네스가
   격리 브랜치를 만든다 — 아래 "무인 실행" 절 4번 참조). 사용자가 이미 만든 토픽 브랜치에서
   돌리려면 `"current"` 로 바꾼다. **1단계에서 브랜치를 분기해 체크아웃했다면 `"isolate"` 를
   그대로 두고 `base_branch` 만 분기 기준 브랜치(예: `develop`)로 맞춘다** — 하네스가 그
   브랜치를 작업 브랜치로 삼는다.

**참고:** `templates/` 폴더에 PLAN/NOTES/STATE.json 템플릿이 있음. 그대로 채워 쓰기.

**산출물:** 3개 파일(PLAN/NOTES + STATE.json, STATE 의 phase 별 `next_steps` 포함) + 사용자 1차 확인

### 3단계: Phase 실행 (반복)

**목적:** Phase 하나를 끝내고 다음으로 넘어간다.

**한 phase 의 흐름:**
1. `TaskUpdate` 로 해당 task 를 `in_progress` 로
2. STATE.json 의 이 phase `next_steps`(비어 있으면 PLAN.md 의 해당 phase 항목)를 그대로 따라 실행
3. 커밋은 의미 단위로 분리 (파일 이관 / 의존성 / 빌드 검증 등)
4. 검증 명령 실행 → 통과 확인
5. STATE.json / NOTES.md 갱신
   - **STATE.json: 이 phase status 를 "done" 으로, 다음 phase 의 `next_steps` 를 상세 작업 단계로 채운다** (유인 모드에서는 세션이 직접 — 빼먹으면 나중에 `fw run` 이 재실행하거나 다음 세션이 단계 없이 시작한다)
   - **phase 를 새로 추가했다면 PLAN 의 phase 표에도 같은 행을 추가한다** (두 파일은 항상 같은 목록 — 위 §산출물 3종 참조)
   - NOTES: 이번 phase 에서 얻은 이관 메모/리스크/트러블슈팅 갱신 (권장 — 상태 표 금지)
6. STATE/NOTES 갱신도 한 commit 으로
7. push (또는 사용자 합의된 워크플로우 — develop 직접 / topic branch / squash 등)
8. `TaskUpdate` 로 `completed`

**커밋 메시지 규칙 (사용자가 따로 지정하지 않은 경우):**
- conventional commits: `feat(<module>):` / `chore(<module>):` / `fix(<module>):` / `docs(<module>):` / `test:`
- 본문에 출처→목적지 매핑, 검증 결과, 트러블슈팅 메모 포함
- 작성자 이메일 사용자 계정 (예: `git config user.email`) 확인

**phase 간 전환 시 사용자에게 묻는다:**
- "다음 phase 로 바로 진행할까요?"
- "지금 push / PR 만들까요, 나중에 한꺼번에?"

### 4단계: Verify (병렬 검증)

**목적:** 큰 phase 가 끝났을 때 누락/오차 점검.

**언제:**
- 여러 source 를 새 위치로 이관했을 때 (sed 기계적 치환은 누락하기 쉬움)
- 사용자가 "잘 옮겨졌는지 확인" 요구
- 마이그레이션 마무리 직전

**방법:**
- 사용 가능한 병렬 agent/subagent 도구로 검증 에이전트 병렬 실행 (보통 source 별 1개)
- 각 에이전트는 원본 파일 목록 → 매핑 규칙 → 새 위치 존재 여부 → diff 비교
- 결과를 종합해서 누락/의심 케이스 보고
- 발견된 누락은 별도 phase 로 처리하거나 즉시 보강

### 5단계: Wrap up (마무리)

**목적:** 작업 완료 + 다음 세션이 README 만 봐도 알 수 있게.

**해야 할 일:**
- README 갱신 (필요 시 신규 작성)
- NOTES 최종본 정리 + STATE 최종 상태 확인 (`fw status`)
- (선택) `release/<date>` 브랜치 또는 main PR

## 의사 결정 흐름도

```
사용자 요청 받음
  ↓
[큰 작업인가?] ── No → 일반 작업, 이 skill 발동 X
  ↓ Yes
[모호한가?] ── Yes → 현재 환경의 사용자 질문 수단 (1단계)
  ↓ No
[docs/<workflow>/ 있나?] ── No → 2단계 (PLAN/NOTES/STATE.json 작성, STATE next_steps 포함)
  ↓ Yes (이어받기)
PLAN.md + STATE.json 의 next_steps 읽기 (현황은 `fw status`)
  ↓
3단계 phase 실행
  ↓
검증 + STATE/NOTES 갱신 + commit
  ↓
[더 남았나?] ── Yes → 다음 phase
  ↓ No
4단계 verify (필요 시) → 5단계 wrap up
```

## 사용자에게 물어야 할 것 (체크리스트)

워크플로우 초기에 일반적으로 합의해야 하는 것들:

- [ ] 작업 디렉토리 / docs 위치 (`docs/<name>/` 또는 다른 위치)
- [ ] 브랜치 전략 (develop 직접 / topic 브랜치 / stacked PR 등)
- [ ] 커밋 author (이메일/이름)
- [ ] 커밋 메시지 스타일 (conventional / 자유)
- [ ] PR 생성 시점 (phase 마다 / 전체 끝나고 / 안 함)
- [ ] 검증 명령 (예: `./gradlew clean build`, `pnpm test`)
- [ ] 누락/모호한 결정은 묻고 진행

## 산출물 위치 권장

```
<repo-root>/
└── docs/
    └── <workflow-name>/        # 예: migration, refactor-auth, feature-checkout
        ├── PLAN.md             # 마스터 플랜 + §핵심 결정 표 + §용어 표
        ├── NOTES.md
        └── STATE.json          # 하네스(fw)용 기계 상태, phase 별 next_steps 포함
```

**3종만 쓴다.** 결정 로그를 별도 파일(`DECISIONS.md` 등)로 분리하지 않는다 — 결정은
PLAN §핵심 결정 표에 두고, 하네스가 그 절을 파싱해 무인 세션에 주입한다.

## 다음 세션이 이어받는 방법

다음 세션의 AI 가 사용자 첫 메시지를 받으면 즉시:

1. `cat docs/<workflow>/PLAN.md docs/<workflow>/NOTES.md` 읽기
   (phase 진행 현황·다음 작업 단계는 `fw status docs/<workflow>` 또는 STATE.json 의
   해당 phase `next_steps` — STATE.json 이 진실 소스)
2. 거기서 정의된 next_steps 를 그대로 실행 (비어 있으면 PLAN.md 의 해당 phase 항목 참고)
3. 끝나면 동일한 갱신 사이클 (STATE status/next_steps + NOTES)

이 skill 이 발동된 새 워크플로우는 **PLAN.md + STATE.json(next_steps) + NOTES.md 세 파일이
있으면 어디서든 이어받을 수 있어야** 한다.

## 함께 사용하는 commands

- `/feature-workflow:start` — 새 워크플로우 시작 (1~2단계 자동 진행)
- `/feature-workflow:resume` — 기존 워크플로우 이어받기 (PLAN+STATE(next_steps) 읽고 다음 phase 실행)
- `/feature-workflow:notes` — 현재 진행 상태로 NOTES + STATE 갱신 (구 HANDOFF 체계 대체)
- `/feature-workflow:verify` — 병렬 에이전트로 검증

## 안티 패턴 (절대 하지 말 것)

- ❌ 1단계 건너뛰기 — 모호한 채로 phase 진행
- ❌ 한 PR 에 여러 phase 섞기
- ❌ STATE/NOTES 갱신 빼먹기 — 다음 세션이 헤맨다
- ❌ 사용자 합의 없이 임의로 author/브랜치 전략 변경
- ❌ 검증 명령 결과 확인 안 하고 다음 phase 로 넘어가기
- ❌ 결정 로그 누락 — "왜 이렇게 했지" 가 1주 뒤 미스터리가 됨
- ❌ **뒤집힌 결정을 지우거나 덮어쓰기** — `superseded by D<n>` 으로 남겨야 함. 지우면 다음
  세션이 폐기된 결정을 되살린다
- ❌ **결정을 AI 의 메모리나 채팅 맥락에만 두기** — 다른 세션·다른 AI·서브에이전트는 그걸
  못 읽는다. 프로젝트 문서(PLAN §핵심 결정)에 있어야 이어받을 수 있다
- ❌ **용어를 세션마다 새로 지어 쓰기** — 여러 세션에 걸친 워크플로우에서 용어 드리프트는
  하위호환 부채로 굳는다. PLAN §용어를 먼저 보고, 새 용어를 도입하면 표에 추가
- ❌ 기존 결정과 충돌하는 상황을 발견하고도 "대충 절충해서" 진행 — 즉시 멈추고 물어야 함
