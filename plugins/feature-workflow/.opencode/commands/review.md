# /feature-workflow:review

phase 산출물을 **서로 다른 렌즈의 검토관 에이전트**로 적대 검토한다. 목적은 칭찬이 아니라
출고 전에 실제 결함을 잡는 것 — 검증된 실측(connection-graph 워크플로우, 2026-08-25):
3라운드 검토가 확정 결함 16건을 출고 전에 잡았고, 그중엔 "완전해 보이는 불완전 지도"
(침묵 탈락), 게시 경로 미배선(기능 출구 차단) 같은 혼자서는 운영에서야 발견됐을 것들이 있었다.

## 사용법

```
/feature-workflow:review            # 직전 phase 산출물 자동 파악 (NOTES/STATE 기반)
/feature-workflow:review {대상 설명}
```

## 검토관 구성 — 렌즈가 겹치면 낭비, 나뉘면 그물

변경량에 비례해 투입한다:

| 변경 규모 | 구성 |
|---|---|
| 대형 (새 서브시스템·파서·파이프라인) | **3인 병렬**: 개발(코드 결함) · 도메인(내용 허위/누락) · 평가(측정 정직성·검출력) |
| 중형 (기능 1개·문서 세트) | 1~2인 (도메인 또는 개발+평가 겸임) |
| 소형 (버그픽스·문서 수정) | review 생략 가능 — 기존 테스트/lint 로 충분 |

렌즈 정의:
- **개발**: 코드 경로의 실제 오류 — 파싱/경계/방향 의미론/침묵 실패. 실데이터로 재현.
- **도메인**: 산출물 **내용**의 허위와 누락 — 근거 문서와 전수/표본 대조. 접합부(여러
  출처를 이어붙인 문장)를 우선 표본으로 — 창작이 스며드는 곳이다.
- **평가**: 측정으로서의 정직성 — 게이트 검출력의 사각, 침묵 캡/탈락, 과대 판정,
  "통과했다"는 주장이 실제로 무엇을 보증하는지.

## 검토관 프롬프트에 반드시 넣을 것 (전부 실측으로 효과 확인된 규칙)

1. **재현 강제**: "그럴듯한 추측 금지 — 실제 데이터로 재현하거나 코드 경로를 정확히 짚어
   CONFIRMED 인 것만 보고. 확인 못 하면 보고하지 마라. 발견이 없으면 '없음'이라고 말하라."
2. **집중 의심 지점**: 오케스트레이터가 아는 약한 곳을 번호로 나열해준다 (검토 효율이
   수 배 오른다). 마지막 항목은 항상 "그 외 네가 발견한 모든 실제 결함".
3. **출력 형식 고정**: `심각도 | 위치 | 결함 한 문장 | 재현 증거 | 처방 한 문장`,
   최대 5~6건 심각도순. **"결함 아님 (확인 결과)" 절 포함** — 검토했지만 문제없던
   의심 지점을 명시해야 오케스트레이터가 재검토를 반복하지 않는다.
4. **읽기 전용**: 검토관은 파일을 수정하지 않는다 — 교정은 오케스트레이터 몫.
5. 실행/재현 환경(경로·명령)을 프롬프트에 그대로 준다.

## 오케스트레이터 절차

1. phase 산출물·변경 규모 파악 → 검토관 수·렌즈 결정, **병렬 spawn** (background).
2. 검토관이 도는 동안 **검토 대상 파일을 수정하지 않는다** (검토가 꼬인다).
   충돌 없는 다른 작업(타 레포 커밋, 문서)은 진행 가능.
3. 결과 도착 시 **지적을 그대로 믿지 말고 재검증한다** — 검토관도 틀린다
   (실측: 검토관이 기대한 엣지가 데이터에 근거 없어 기각한 사례). 확정된 것만 교정.
4. 교정마다 가능하면 **회귀 방지 장치로 박제**: 잡은 허위는 네거티브 게이트로,
   빠진 출구는 테스트로, 침묵 탈락은 자기검증 리포트로.
5. NOTES.md 에 기록: "N인 검토 → 확정 결함 M건 반영" + 상/중/하 내역 + "결함 아님" 판정.
6. 교정 완료 후 검증(테스트/lint/게이트) 재실행 → 커밋.

## 안티 패턴

- 검토관에게 "검토해줘"만 주는 것 — 의심 지점 없는 검토는 표면을 핥는다
- 지적을 재검증 없이 반영 — 검토관의 그럴듯한 오보가 코드에 들어간다
- 같은 렌즈 N명 — 중복 발견만 늘고 사각은 그대로다
- 검토 중 대상 파일 수정
- 결함을 기록만 하고 회귀 방지 장치 없이 넘어가는 것 (같은 결함이 돌아온다)
